# admin-bff

**Владелец:** команда Admin-контура. **Bounded context:** сессии сотрудников в браузере, CSRF, rate limit, RBAC/step-up и агрегация API доменов для admin-web. Своих данных в БД нет; в Redis — сессии, кэш principal и счётчики лимитов.

Стек: Node 22, Fastify 5, `@tilhero/ts-common` (контекст трассировки, ErrorBody, внутренний JWT v2 с `actor`, circuit breaker, health), ioredis. Порт 8002.
Публичный контракт — `packages/contracts/src/admin.ts` (единственный источник типов), внутренние — `docs/sprint2/INTERNAL_API.md`.

## Как это работает

```
браузер ──▶ admin-web (Caddy) ──/admin/v1/*──▶ admin-bff ──внутренний JWT v2 (kid=iss=admin-bff, aud=<домен>,
            один origin, cookie first-party       │          actor {id, role, name, permissions})──▶ admin-identity,
                                                  │                                                   user-admin, identity-consent,
                                                  └── Redis: sess:<sha256(id)>, principal:<staff_id>, rl:*   support, audit, experience-config,
                                                                                                             source-registry, discovery,
                                                                                                             provider-gateway, events
```

- **Публичного домена нет.** admin-web проксирует `/admin/v1/*` на `http://${{admin-bff.RAILWAY_PRIVATE_DOMAIN}}:8002`; `*.up.railway.app` — public suffix, поэтому только один origin. CORS не включается.
- **Сессия:** cookie `__Host-tilhero_admin` (Secure, HttpOnly, SameSite=Strict, Path=/, без Domain) с непрозрачным id (32 случайных байта). В Redis ключ — `sha256(id)` (дамп Redis не даёт готовых cookie), HASH `{staff_id, session_version, created_at, last_seen_at, step_up_until, csrf_token, ip_hash, ua_hash, impersonating}`. Бездействие 30 мин и абсолютный срок 8 ч → `401 SESSION_EXPIRED`. При входе id всегда новый, прежняя cookie браузера удаляется (session fixation). Другой User-Agent с той же cookie → сессия отзывается.
- **Ротация id** (смена пароля, step-up) — атомарный Lua-скрипт: старая сессия должна существовать и не быть замещённой, иначе новая не создаётся (параллельный logout побеждает → `401`). После step-up старый id ещё 15 с действует **без** step-up и без продления (запросы, ушедшие до ответа step-up, не выбрасывают на вход); logout по любому из двух id удаляет обе. Повторная ротация замещённого id (две вкладки одновременно завершают step-up/смену пароля) → `409 SESSION_ROTATED` **без** Set-Cookie (новая cookie, выданная первой вкладке, не стирается; TOTP-код и пароль не тратятся — проверка до вызова admin-identity); клиент повторяет запрос с новой cookie.
- **Фоновые запросы:** заголовок `X-Background: 1` (опрос дашборда/очереди admin-web) — запрос обслуживается, но `last_seen_at` не обновляется, т. е. idle-таймер 30 мин идёт. Любой другой запрос продлевает сессию. В admin.ts заголовка нет — см. «Отклонения».
- **Отзыв:** principal сотрудника (`GET admin-identity /internal/v1/staff/{id}/principal`) кэшируется в Redis ≤ 30 с; статус ≠ ACTIVE, другая `session_version`, 404/403 → `401 SESSION_REVOKED` и удаление сессии. Изменения через этот BFF (смена пароля, PATCH сотрудника, сбросы) сбрасывают кэш сразу (кэш не заполняется ответом шага смены пароля — следующий запрос перечитывает admin-identity). Смена своего пароля → текущая сессия получает новый id, прочие отзываются ростом `session_version`.
- **CSRF:** все не-GET — заголовок `X-CSRF-Token` = `Me.csrf_token` (сравнение за постоянное время) + `Origin` = `ADMIN_WEB_ORIGIN` (без Origin — только `Sec-Fetch-Site: same-origin`) → иначе `403 CSRF_INVALID`. Шаги входа (до сессии) — проверка Origin.
- **RBAC декларативно:** каждый маршрут `/admin/v1/*` объявляет `publicAuth` / `authenticated` / `requirePermission(...)` / `requireRole(...)` и при необходимости `requireStepUp()`; маршрут без объявления не регистрируется (приложение не стартует). Проверка — в `onRequest`, **до** разбора тела и вызова домена; домены проверяют `actor.permissions` повторно.
- **Step-up:** `POST /admin/v1/auth/step-up {code}` → TOTP в admin-identity → новый id сессии (новая cookie) с `step_up_until = now + 5 мин`. Требуется на POST/PATCH staff, reset-password/reset-mfa, PUT roles, approve/reject, POST sources, PUT discovery/pause → иначе `403 STEP_UP_REQUIRED {permission}`. **Условный step-up** — PATCH sources: только если тело меняет `event_domains`, `media_domains`, `enabled` или `tier`. Без свежего step-up BFF читает текущий источник (`GET source-registry /internal/v1/sources/{id}`) и сравнивает: домены — как множества, прочие — по значению; `expected_version` ≠ текущей версии → step-up обязателен (сравнивать не с чем). Домен применяет PATCH только к `expected_version`, поэтому гонка «сверили одну версию — записали другую» невозможна. Со свежим step-up сверки нет.
- **Rate limit** (Redis, фиксированное окно 1 мин, общий для инстансов): вход 10/мин с IP (IPv6 — по /64) и 5/мин на email (в ключе — хеш); шаги по challenge 30/мин с IP и 5/мин на challenge; step-up и смена пароля 5/мин на сотрудника; прочее 300/мин на сотрудника. → `429 RATE_LIMITED {retry_after}` + `Retry-After`.
- **Ошибки:** ErrorBody. 4xx доменов и `501 AUTH_MODE_UNAVAILABLE` — как есть (код, статус, details); недоступность/таймаут/прочие 5xx/битый ответ/отказ внутренней авторизации → `503 UPSTREAM_UNAVAILABLE {service}`. Осознанный 5xx домена маршрут может перевести в свой код (`CallOptions.mapServerError`): kill switch → `503 AUDIT_UNAVAILABLE`. Адрес домена спринта 4 не задан → `503 FEATURE_UNAVAILABLE {service}` «Раздел ещё не настроен» (домен не вызывается). Сбой Redis → 503 (fail-closed).
- **Имена сотрудников** (как `assignee_name` у тикетов): `Source.updated_by_name`, `SourceChange.actor_name`, `AiBudget.paused.by_name`, `ReviewDetail.decided_by_name` — BFF подставляет через admin-identity `GET /admin/v1/staff/lookup` (кэш 60 с, `src/routes/staffNames.ts`); lookup недоступен → `null`, экран работает.
- **Порядок выкладки спринтов 4–6:** `SOURCE_REGISTRY_URL`, `DISCOVERY_URL`, `PROVIDER_GATEWAY_URL`, `EVENTS_URL`, `OFFERS_URL`, `NEWS_URL`, `WATCH_URL` необязательны и в stage/prod. Код может выйти раньше переменных: без адреса маршруты раздела отвечают `503 FEATURE_UNAVAILABLE` (для news/watch — с названием неподключённого сервиса в тексте), остальная админка работает, при старте — WARNING `sprint 4-6 domain urls are not configured` со списком переменных. `/health/ready` такого домена на дашборде — `down` (дашборд их не опрашивает).
- **Аудит действий BFF** (`POST audit /internal/v1/records` с actor): `dev.impersonate` (без записи режим не включается), резервный `auth.logout`, если admin-identity недоступен. Вход, MFA, смена пароля, logout — аудирует admin-identity; reveal — identity-consent (синхронно, без аудита значение не выдаётся).
- **Ответы по схеме контракта** (`src/responses.ts`, fast-json-stringify): клиент получает только поля admin.ts (client-view — bff.ts `Ticket`), служебные поля доменов отбрасываются (ревью спринта 1, T2). `shape<T>()` требует ровно ключи типа контракта — расхождение с admin.ts ломает `tsc`; обязательные поля — в `x-contract-required`. Сериализатор их не требует и молча подменяет null на ""/0, поэтому тесты (`routes.test.ts`) проверяют каждый 2xx-ответ до сериализации строгим Ajv по той же схеме. Маршрут `/admin/v1` без схемы ответа не регистрируется. Временный пароль (создание сотрудника, reset-password, approve) — только в ответе, `Cache-Control: no-store`, ключ `temporary_password` вычищается из логов.
- **A43 `redactSensitive`:** `ai_conversations[].prompt/response` → null без `ai.content.read` (до спринта 6 список пуст).

## Отклонения от контракта и запросы к общему коду

- `GET /admin/v1/support/stats` — нужен admin-web (`Support.stats`), в admin.ts нет; тип ответа — как блок `Dashboard.support` без `available`. Добавить маршрут и тип `SupportStats` в admin.ts.
- `GET /admin/v1/experience/{admin|miniapp}/current` — admin.ts не даёт способа прочитать тему админки сотруднику без `config.read` (A46 «тема из конфига» работает только у super_admin/operations). Добавить маршрут и тип ответа (`AdminExperienceConfig`/`MiniAppExperienceConfig` experience-config) в admin.ts.
- Dashboard: тип блоков `users`/`support` — только `available: true`, поэтому при недоступности источника данных BFF отвечает `503 UPSTREAM_UNAVAILABLE {service}` целиком (а не нулями). Для частичной деградации нужен вариант `{available: false; degraded: true}` в admin.ts.
- `GET|PUT /admin/v1/support/sla-policies`: формы в admin.ts нет — схема ответа по support `SlaPoliciesOut` (как локальный тип admin-web `SlaPolicy`); добавить `SlaPolicy`/`SlaPolicies` в admin.ts. Ответ эскалации — форма элемента `StaffTicket.escalations`. `experience/{app}/current` — свободный объект (типа нет).
- Заголовок `X-Background: 1` (запрос не продлевает сессию) — описать в шапке admin.ts рядом с CSRF; admin-web должен ставить его на фоновый опрос.
- Новый код ошибки `403 IMPERSONATION_NOT_ALLOWED {role}` (dev) — добавить в комментарий `/admin/v1/dev/impersonate`.
- **Спринт 4:**
  - Счётчик OPEN очереди проверки (бейдж меню) admin-web считает по первой странице `GET /admin/v1/review?status=OPEN&limit=100` (фоновый опрос раз в минуту, `X-Background: 1`; больше 100 → «99+»). Отдельного маршрута статистики нет; для точного числа нужны `GET events /internal/v1/review/stats` (`{open}`) и `GET /admin/v1/review/stats` + `ReviewStats` в admin.ts.
  - `PUT /admin/v1/discovery/pause`: provider-gateway отвечает на сбой аудита `503 UPSTREAM_UNAVAILABLE {service: "audit"}`; BFF переводит его в `503 AUDIT_UNAVAILABLE` (как и будущий собственный код домена `AUDIT_UNAVAILABLE`). Запрос к provider-gateway: отдавать `AUDIT_UNAVAILABLE`.
  - `GET /admin/v1/review`: экрану нужен фильтр «по причине», в контракте (§6, §7) его нет — добавить `reason=` в events и admin.ts.
  - Ответы решений очереди: admin.ts — `{review, event_id}` / `{review}`; если events вернёт сам `ReviewDetail`, BFF заворачивает его (event_id — из `review.event_id`).
  - `PUT /admin/v1/discovery/pause` → `AiBudget` (admin.ts), а §3.5 называет ответ provider-gateway «состоянием»: если provider-gateway вернёт только `{paused, reason, by, at}`, BFF дочитывает `ai_web/budget`.
  - `POST /admin/v1/discovery/runs` без `max_provider_calls` отправляет в discovery явный бюджет 200 (потолок admin.ts), а не полагается на `DISCOVERY_MAX_PROVIDER_CALLS_PER_RUN`.
  - Условный step-up PATCH sources не виден в реестре маршрутов (`adminRoutes[].stepUp = false`) — проверяется в обработчике.
- **Спринт 5:**
  - `TravelProviderStatus.last_error.at` — `string` в admin.ts, но `ProviderStatus` provider-gateway спринта 4 отдаёт только `last_error_code` (время лежит в Redis `last_error_at`). BFF принимает `last_error: {code, at}` или пару `last_error_code`/`last_error_at`; если времени нет — `at: null` (admin-web пишет «время неизвестно»). Запрос к provider-gateway: отдавать `last_error_at`.
  - `OfferSnapshotAdmin.offer`/`trip` — `unknown` в admin.ts: BFF отдаёт нормализованную форму `bff.Offer` / `OfferSetView["trip"]` с отличиями: `deeplink` компонента — `string | null` (не https → null), у отеля нет `lat`/`lon`/`photo_url`, `map` — только https-ссылки или `null`; у перелёта `airline` может быть `null`; причина `BAD_DATA` — компонент не прошёл проверку. Предложение: описать эту форму в admin.ts (`OfferAdminView`).
- **Спринт 7:**
  - Ответы ai-control, ai-concierge и `providers/ai/*` нормализуются одним описанием (`src/codec.ts`, `routes/aiCodecs.ts`): то же описание даёт схему ответа; испорченный ответ → `503 UPSTREAM_UNAVAILABLE {service}`, в лог — только путь поля.
  - `POST …/alerts/{id}:ack`, `…/pricing/versions/{v}:activate` — в Fastify параметр с буквальным `:` не поддерживается: маршруты `…/alerts/:ref`, `…/versions/:ref` с проверкой `^<uuid>:ack$` / `^<версия>:activate$` (снаружи пути как в §6).
  - `AiAgentRuntimeState.month/degrade_at_pct/degraded_mode` — nullable и `AiBudgetOverview.control`: без ai-control обзор строится из provider-gateway (аварийная остановка не зависит от ai-control).
  - `AiRequestDetail.price_catalog_versions[]` вместо `price_catalog_version` (у ai-control — строка или список); `SkillDetail.versions_full` — полные карточки версий (`versions` — краткие, как в списке); `SkillCompare.fields/runs` — массивы со значениями JSON-строкой (у ai-control — словари).
  - `AdminUserCard.ai_conversations` — только метаданные (`AdminAiConversation`), `redactSensitive` удалён (содержимого в карточке нет никогда). `Dashboard.ai_usage` — `DashboardAiUsage` (данные ai-control вместо заглушки «спринт 6»).
  - Ack алерта без Idempotency-Key от клиента — BFF подставляет `ack-<id>` (ack идемпотентен по смыслу).
  - Ревью 7: `AiLimitValues.concierge_daily_usd/evaluation_daily_usd` — необязательные (`null` у provider-gateway 6.1; испорченное значение — по-прежнему 503). `warnings[]` команд ai-control (PATCH агента, PUT уровня) — `AiCommandWarning {code, message, details}`: только скаляры, испорченное предупреждение отбрасывается (команда уже выполнена). Причина в DELETE уровня и сброса уровня пользователя — в теле, не в URL (браузер и прокси пишут URL в журналы); к ai-control — по-прежнему `?reason=` внутреннего вызова (INTERNAL_API §2.7).
- **Спринт 8:**
  - `Dashboard` = `DashboardV2` (прежний вид спринтов 1–7 удалён); прежний опрос `/health/ready` шести доменов убран — «Здоровье системы» из ops-monitor `ops/summary`. `DashboardAi` = `{kpi, budgets}`: сбой `budgets/overview` не прячет расходы (`budgets: null`). Блок `users` требует `active_in_period`/`active_today` (user-admin спринта 8): старый ответ — «нет данных», не нули.
  - Ответы ops-monitor — списки; BFF отдаёт `{items}` (как остальные списки admin.ts). `ProviderHealth.probe_supported` — BFF. `OpsAlert.acked_by_name` — staff/lookup.
  - Колокольчик: важность алерта AI — 100 % или автопауза → critical, 90 % и «без цены» → warning, 70 % → info; `counts` — по неподтверждённым.
  - Ack оповещения ops — без step-up (как ack алерта AI спринта 7; план §7.5 — `ops.kill_switch`); step-up — только у команд DLQ.
  - A45: в admin-bff нет зависимостей от n8n; экраны пользователей, поддержки и дашборд n8n не вызывают.

## Безопасность

- В браузере нет токенов и секретов: только HttpOnly cookie и CSRF-токен в памяти admin-web. `staff_id` — только из сессии.
- Тела — строгие JSON Schema (`additionalProperties: false`, без приведения типов): лишнее поле → `422 VALIDATION_ERROR {in, field, errors}` без эха значений.
- Пароли, коды, challenge, секрет MFA, временный пароль, cookie, CSRF-токен, email, тексты сообщений, reason, полный Telegram ID — никогда в логах: redact-пути pino + рекурсивная вычистка ключей; access-лог пишет шаблон маршрута (не URL с `q=`), сотрудник — псевдоним `user_pid`. Секрет MFA и временный пароль — только в ответе своего шага.
- Ответы — `Cache-Control: no-store`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Cross-Origin-Resource-Policy: same-origin` (спринт 9, SEC-12); CORS не включается.
- Спринт 9: оповещения ops-monitor — виды `service_down`, `deletion_stuck`, `rate_limit_spike`, `rate_limit_unavailable` и `runbook_url` (только https ≤ 300, иначе `null`) в `ops/alerts` и колокольчике; `Idempotent-Replayed: true` домена (команды DLQ, ack, повтор удаления, лимиты) передаётся клиенту.
- Имперсонация (`ENV=dev`) только сужает: примерить можно лишь роль, все права которой (матрица по умолчанию) у сотрудника уже есть (иначе `403 IMPERSONATION_NOT_ALLOWED`); эффективные права — права этой роли. Роль в actor-токене и проверки `requireRole` — по **настоящей** роли (при имперсонации роль маршрута должна совпасть и с примеряемой). Вне `ENV=dev` маршрута нет (404), а поле `impersonating` в сессии игнорируется.
- **Адрес клиента** (лимиты входа, `ip` в admin-identity и аудите): цепочка браузер → edge Railway → Caddy admin-web (`trusted_proxies 0.0.0.0/0 ::/0` — Caddy дописывает адрес edge в `X-Forwarded-For`) → admin-bff. Приходит `X-Forwarded-For: <подделка клиента…>, <реальный клиент>, <edge>`, сокет — Caddy. `TRUST_PROXY_HOPS=2` доверяет ровно двум последним звеньям (сокет Caddy и запись edge), поэтому `req.ip` = реальный клиент, а подставленные клиентом адреса левее игнорируются (тест в `security.test.ts`). Если перед admin-bff появится ещё один прокси (или Caddy перестанет дописывать XFF) — изменить значение, иначе лимит окажется на адресе прокси или будет обходиться подделкой.

## Runbook

> Эксплуатация через браузер (Railway, админка, оповещения ops-monitor): [docs/runbooks/admin-bff.md](../../docs/runbooks/admin-bff.md). Ниже — технические детали для разработчика.

- **Деплой (Railway):** `RAILWAY_DOCKERFILE_PATH=services/admin-bff/Dockerfile`, контекст — корень репозитория; без публичного домена; healthcheck `/health/ready`. Локально: `docker build -f services/admin-bff/Dockerfile .`. Ключ admin-bff должен быть в общей `INTERNAL_JWT_PUBLIC_KEYS` доменов (`infra/railway/setup.py` → ISSUERS).
- **`/health/ready` = 503 `redis: down`:** проверить Redis и `REDIS_URL`; пока Redis недоступен, вход и сессии невозможны (503).
- **Массовые `503 UPSTREAM_UNAVAILABLE {service}`:** смотреть `details.service` и строки `domain unavailable` (`upstream`, `upstream_status`, `upstream_code`). `INTERNAL_TOKEN_*|CALLER_NOT_ALLOWED|ACTOR_NOT_ALLOWED` — ключ/разрешённые вызывающие у домена.
- **Все получают `403 CSRF_INVALID`:** `ADMIN_WEB_ORIGIN` не совпадает с origin admin-web (схема, хост, порт).
- **Завершить все сессии сотрудника:** PATCH статуса или сброс пароля/MFA в admin-identity (рост `session_version`) — в течение ≤ 30 с; немедленно — `redis-cli del admin-bff:principal:<staff_id>`. Все сессии сразу: `redis-cli --scan --pattern 'admin-bff:sess:*' | xargs redis-cli del`.
- **Ложные 429 на входе:** проверить `TRUST_PROXY_HOPS` и что Caddy дописывает XFF (иначе все клиенты — один IP edge/Caddy), затем лимиты.
- **Первый администратор:** создаётся admin-identity из `ADMIN_BOOTSTRAP_EMAIL/PASSWORD`; после первого входа переменные удалить.
