**🟡 P-1 [Производительность / Надёжность] plan:tick обрабатывает каждый план несколькими отдельными запросами в одной транзакции. При пиковом слоте это длится минуты и забирает весь пул learning-plan**

> **Статус (повторная проверка, HEAD 7fe6d7f):** ✅ **исправлено в a3b9a84.** Tick идёт пачками, у каждой пачки своя короткая транзакция и фиксированное число запросов (`domain/tick.py:158-221`). Один tick за раз держит сессионную `pg_try_advisory_lock`, повтор сразу отвечает `{skipped: true}` (`:260-280`). Повторил свои замеры (те же скрипты): 20 000 напоминаний — **2,8 с** (было 63,2). 10 000 пропусков — **1,07 с** (было 25,4). 50 000 напоминаний с двумя повторами n8n (`tick_pool2.py`): tick 6,2 с, оба повтора `skipped: true`, `GET /me/plan` ученика во время tick — **0,2 с** (было 28 с). Регрессий не нашёл: блокировка снимается до возврата соединения в пул, при сбое соединение закрывается. Отметки `slot_marks` и outbox пачки фиксируются вместе. Удаление плана ждёт только короткую транзакцию своей пачки.

📍 `services/learning-plan/src/tilhero_learning_plan/domain/tick.py:100-141` (`_process`: на каждый план со слотом — `_still_present`, `_has_activity`, `_mark`, `streak_days` (2 запроса), `emit`; для пропуска ещё `_consecutive_missed`), `:144-175` (все планы — в одной транзакции вызывающего); `api/scheduler.py:22` (`async with rt.transaction()` на весь tick); `settings.py:11-12` (пул 2 + 1); `infra/n8n/workflows/plan-tick.json:48-51` (таймаут 120 с, `retryOnFail: true`, 3 попытки через 5 с).

**Сценарий отказа.** Слот 19:00 по умолчанию и пресет «вечер 19:00», почти все ученики в одной зоне Asia/Tashkent. Значит, большая часть планов попадает в одно окно tick. Обработка идёт по одному плану (~3 мс на план) в одной транзакции:
- 20 000 планов со слотом в окне — **63,2 с** на один вызов. 10 000 пропусков в местную полночь — **25,4 с**. Пустое окно на 20 000 планов — 0,28 с.
- Примерно от 40 000 одновременных слотов вызов дольше таймаута n8n (120 с). n8n повторяет его ещё два раза. Каждый повтор ждёт `FOR UPDATE` на `tick_state` и держит своё соединение.
- Пул 2 + 1 соединения: исходный tick и два повтора занимают все три. Обычные запросы учеников (`GET /me/plan`, `PATCH`, `/activities`) и relay outbox ждут свободного соединения. **Воспроизведено** на 10 000 планов: `GET /internal/v1/me/plan` во время tick с двумя повторами ответил через **28,0 с**. `pool_timeout` у SQLAlchemy по умолчанию 30 с. При 20 000 планов ожидание превысит его, и запрос получит 500 (вероятно, по расчёту).
- Сами напоминания приходят с задержкой на время tick. Удаление плана (сага) тоже ждёт конца транзакции (`FOR KEY SHARE`).

**Воспроизведение:** `uv run python /tmp/rv/scripts/tick_perf.py 20000` → `all due: {'plans_checked': 20000, 'reminders': 20000} 63.18s`. `tick_perf_missed.py 10000` → `missed: 10000 25.41s`. `tick_pool.py 10000` → `learner GET /me/plan during tick: status=200 after 28.0s`.

**Рекомендация.**
1. Обрабатывать пачками со своей транзакцией (`batch_size` уже есть). Отметки `slot_marks` и так обеспечивают идемпотентность. Двигать `last_tick_at` только после всех пачек.
2. Внутри пачки вместо поштучных запросов: один запрос «занятия за даты кандидатов», вставка `slot_marks … ON CONFLICT DO NOTHING RETURNING` сразу для всех, серия и `consecutive_missed` — одним агрегатом на пачку.
3. Повтор n8n не должен ждать блокировку: `pg_try_advisory_xact_lock` или `FOR UPDATE NOWAIT`, занято → 200 `{skipped: true}`.
4. Добавить нагрузочный тест (10–20 тыс. планов) в регресс.

- решить может свежий аккаунт без принятых `terms` и `privacy`. Сервер проверяет только 18+, а Mini App выставляет 18+ прямо в шторке (`GuardianSheet.tsx:36-43`). Данные родителя (`guardian_user_id`) обрабатываются без его согласия с политикой;
- отозвать `granted` нельзя: нет ни команды родителя, ни команды подростка. Событие `consent.*` не выпускается, аудит согласий подростка видит только `user.profile.updated.v1`.

**Рекомендация:** при `accept` и `decline` создавать для подростка запись `Consent` (основание `guardian`, `granted_by_user_id = родитель`, `policy_version`, `policy_text_sha256`, `evidence_hash`, `locale`) и выпускать `consent.accepted.v1` / `consent.revoked.v1`. Требовать у родителя действующее собственное согласие: 403 `CONSENT_REQUIRED`, а Mini App сначала показывает политику. Добавить отзыв согласия родителем: `guardian_consent → declined`, необязательные цели подростка снимаются. В таблице `guardian_consent_requests` INTERNAL_API §1 этих полей нет — сначала дополнить контракт.

## Проверено — замечаний нет
- **AuthZ.** Во всех доменах явные списки вызывающих: identity — `telegram-bff`; `/delivery` — только notifications; `/public` — social и notifications; `bot-status` — только bot-gateway. Клиентские API learning-plan, social, notifications, experience-config и support — только `telegram-bff`; staff — только `admin-bff`; `/transactional` — только identity-consent; `/internal/v1/messages` — только notifications, на отдельном порту. `user_id` во всех клиентских роутерах берётся из `sub` токена.
- **IDOR.** Чужой ученик и ребёнок другого родителя → 404 `LEARNER_NOT_FOUND` (`service.py:371-388`). Чужое приглашение → 404 (отзыв, карточка только после `:open`, принятие и отказ только с `redemption`). Чужие id в `inbox:read` и `seen` игнорируются.
- **Токены.** Приглашение — 192 бита (HMAC-SHA256, 32 символа base64url), в БД только sha256. Семья — 7 дней, друг — 30 дней, оба одноразовые; повторная активация → 409. Согласие родителя — 256 бит, sha256, 7 дней. Решение принимается один раз; новая ссылка и удаление отзывают прежнюю.
- **Секреты в prod** (наследие aievent): `ENV`, `INTERNAL_JWT_SECRET` ≥ 32 и не dev, EdDSA-ключ обязателен, `INVITE_TOKEN_KEY` обязателен. Сравнение `SCHEDULER_TOKEN` за постоянное время, внутренний JWT на входе планировщика → 403.
- **PII в логах.** `hide_parameters=True`, `pseudonymize(user_id)`, в access-лог пишется шаблон маршрута (токен `gc_` в пути не попадает). Имён и Telegram ID в событиях нет: имена отрисовываются только в момент отправки.
- **Дети.** Возраст аккаунта только 14-17 или 18+. Детский профиль создаёт только 18+, не больше 5. Адресат сообщений ребёнка — опекун (его Telegram ID, блокировка бота и язык). Окно 08:00–20:00 по зоне ребёнка. Детские тексты `*.kid` мягкие, без «потери» и «провала». Детские профили удаляются вместе с аккаунтом: отдельный `request_id` на каждого. Подросток без `granted` получает 403 на необязательные цели и на приглашения.
- **plan:tick.** Окно `(last, now]` не больше 24 ч. DST (провал и повтор времени, пропущенная полночь) проверен скриптом. Идемпотентность через `slot_marks`. Параллельные запуски сериализует `FOR UPDATE` на `tick_state`. Смена графика действует со следующего слота (`schedule_set_at`). Занятие в тот же день отменяет пропуск.
- **notifications.** Порядок политики как в §4. Тихие часы через полночь. Лимит 3 в местные сутки — на ученика, под advisory-lock, с резервом и без двойного счёта при повторе. Сообщение о возвращении (comeback) — не чаще раза в 7 дней. Устаревание: напоминание через 3 ч, пропуск в 22:00. Блокировка бота → `in_app_only` и `telegram.delivery.failed.v1`.
- **«Что нового».** Режимы welcome, updates и none, сегменты по языку и возрасту, не больше 5 заметок. Отметки идемпотентны, черновики не отмечаются. После удаления ученика → 410.
- **Сага удаления.** ACK принимается только от самого домена (`producer == domain`). Повторы и STUCK работают через таймер с `SKIP LOCKED`. Все участники пишут `deleted_users`, чтобы данные не воскресали.
- **outbox и inbox:** `emit` в той же транзакции, inbox-дедупликация в `Runtime.add_consumer`.
