# ADR-0001. Деньги — целые числа: тийины и Telegram Stars

- Статус: **принято** (спринт 8, 22.11.2026, поток 0)
- Отступление от: [CONVENTIONS.md](../CONVENTIONS.md) §2 («Деньги — `Decimal`/`NUMERIC(12,2)` + `currency`»)
- Связано: [docs/sprint8/PLAN.md](../sprint8/PLAN.md) (решение координатора 8), [INTERNAL_API.md](../sprint8/INTERNAL_API.md) §0.4, §1.1

## Контекст
Спринт 8 вводит деньги в двух разведённых каналах: в Mini App — Telegram Stars (валюта `XTR`, только целые звёзды),
на сайте оплаты — сумы через Payme, Click и Uzum. Правило CONVENTIONS §2 (`Decimal` / `NUMERIC(12,2)`, в JSON — строкой
или числом с двумя знаками) писалось до денег и плохо ложится на эти источники:

- **Payme** передаёт суммы целыми тийинами (1 сум = 100 тийинов) — `amount` в Merchant API;
- **Click** присылает `amount` строкой в сумах (`"15000.00"`), а в подписи участвует строка «как пришла»;
- **Uzum** (по сторонним реализациям) — целые тийины;
- **Telegram Stars** — целые звёзды (`total_amount`, `prices[].amount`), без дробной части; вознаграждение за звезду
  и курс к суму задаёт Telegram, они меняются;
- цены сайта целые в сумах (49 000, 129 000), цены в Stars — целые.

Дробные типы добавляют лишние преобразования на каждой границе (JSON-число с двумя знаками превращается в `float` в
JavaScript и в `Decimal` в Python), а «одна сумма + валюта» в одной колонке позволяет случайно сложить сумы со звёздами.

## Решение
1. **Сумы — целые тийины** (`BIGINT`, Python `int`, валюта `UZS`); **Stars — целые звёзды** (`INTEGER`, Python `int`,
   валюта `XTR`). `float`, `Decimal` и `NUMERIC` для денег не используются нигде: в моделях, миграциях, домене, API,
   событиях и клиентах.
2. **Разные поля для разных денег.** В заказе, транзакции провайдера и возврате — `amount_tiyin` и `amount_stars`;
   заполнено ровно одно, второе `NULL` (CHECK в БД, `currency` согласована с провайдером: `XTR` ⇔ `telegram_stars`).
   В каталоге у товара две независимые цены: `price_tiyin` (сайт, кратна 100 — целые сумы) и `price_stars` (Mini App).
3. **Пересчёта между сумами и Stars в домене нет.** Сумма заказа — только из каталога (снимок в заказе). Курсы —
   тоже целые и только для отчётов: «тийинов за 1 USD» (`fx_rates.usd_in_tiyin`) и «тийинов за 1 Star» — оценка
   вознаграждения (`star_rates.star_in_tiyin`), вводят финансы. Пересчёт — в отчётах и финансовом обзоре целочисленно
   (half-up), выручка Stars в сумах — с пометкой «оценка».
4. **Границы:**
   - Click: строка `amount` разбирается целочисленно в тийины по `^\d{1,12}(\.\d{1,2})?$` (иная форма — ошибка -2);
     в ссылку оплаты — `N.NN`, собранная из целых тийинов; подпись — по полям «как пришли»;
   - Payme, Uzum: целые тийины как есть; Stars: целые звёзды как есть (`createInvoiceLink`, `SuccessfulPayment`);
   - JSON API и события: целые числа (`amount_tiyin ≤ 10¹¹` — безопасно для `number` JavaScript, < 2⁵³);
   - фискальный НДС «внутри цены» — целочисленно: `⌊price × p / (100 + p) + ½⌋` (округление подтверждает бухгалтер);
   - клиенты (Mini App, сайт, админка) форматируют целые: «49 000 сум» / «49 000 soʻm», «⭐ 300».
5. **Затраты ИИ** (USD) остаются как в спринте 4 (учёт ai-gateway); в финансовом обзоре они приводятся к целым
   микродолларам и к тийинам по целому курсу USD.

## Последствия
- Плюс: нет ошибок округления и потери точности на границах; суммы сравниваются точно (`AmountMismatch`); сумы и
  звёзды нельзя случайно сложить; один тип на всех языках (`int` / `BIGINT` / `number`).
- Плюс: проверяемость — тест каркаса billing (`services/billing/tests/test_skeleton.py::test_money_is_integer_only`)
  запрещает `decimal`, `Numeric(`/`NUMERIC(` и аннотации `float`/`Decimal` у полей и параметров с `amount`, `price`,
  `tiyin`, `stars`; ревью — пункт «Нет float/`Decimal` в суммах» чек-листа AGENT_BRIEF.
- Минус: отображение всегда делит на 100 (сумы) — форматирование только в клиентах и шаблонах; отчёты в сумах с
  копейками не нужны (цены — целые сумы).
- Минус: частичных возвратов деньгами нет (В11) — тип это не ограничивает, но и не требует дробей.

## Рассмотренные варианты
- `NUMERIC(12,2)` + `currency` (CONVENTIONS §2) — отвергнут: Stars не имеют дробной части, Payme и Telegram работают в
  целых единицах, лишние преобразования и риск `float` в TypeScript.
- Одна колонка суммы + `currency` — отвергнут: сумы и звёзды не сравнимы и не складываются; CHECK на «ровно одно из
  двух» проще ловит ошибки.
- Суммы строками (`"49000.00"`) — отвергнут: разбор на каждой стороне, ошибки формата; строка нужна только Click и
  остаётся внутри его адаптера.

## Область
